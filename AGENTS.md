# docling-scheduler — Agent Guide

`python -m docling_scheduler [--host 127.0.0.1] [--port 8765]` runs a FastAPI app, on loopback by default (the container image binds `0.0.0.0`, behind a Service). It launches [docling-agent](https://github.com/mcaimi/docling-agent) runs as containers (one per shard), either under local Podman or as Jobs on a remote Kubernetes/OpenShift cluster (`SCHEDULER_EXECUTOR`), and monitors them through MLflow and the runtime. It also serves a built [docling-ui](https://github.com/mcaimi/docling-ui) from `SCHEDULER_WEB_DIR` and prints a `/#token=…` URL.

## Boundary with the agent

- **Never import agent code**, not even in tests. The only shared artifact is `src/docling_scheduler/settings-schema.json`, generated by `python -m src.docling_agent --print-settings-schema` in the agent repo and vendored here as-is (don't hand-edit it).
- `contract.py` loads it: `SettingSpec`, `SETTINGS_SPEC`, `SETTINGS_BY_KEY`, `DOCUMENT_GLOBS`, `settings_from_mapping` (env → values, same rules as the agent's loader), and `settings_schema()` (the UI form view). Sensitive settings have no default in the contract. `dynamic_default` names map to callables in `_DYNAMIC_DEFAULTS`, and a callable default is never rendered into a container unless set explicitly. An unsupported `schema_version` fails at import.
- Shards always run in containers, so embedded Chroma / Milvus Lite are rejected (they'd be lost with the container). Each executor declares `ExecutorCapabilities`, and pre-flight branches on them, never on the executor's name:
  - **Podman** (default, local): loopback endpoints are rewritten to `host.containers.internal`, host folders can be mounted, images are checked in the local store.
  - **Kubernetes** (remote clusters only, OpenShift first): S3 sources only; loopback endpoints *that are in use* (per the contract's `depends_on`) are rejected rather than rewritten; images come from a registry (`localhost/` refs are rejected). `SCHEDULER_CONTAINER_MLFLOW_TRACKING_URI` sets the MLflow address pods use when it differs from the scheduler's. Talk to the cluster only through the official `kubernetes` Python client: never shell out to `kubectl` or `oc`.
- Document sources follow the agent's `source_backend`. With `local` (Podman only), `target.host_folder` is required and mounted read-only at `/data/in`. With `s3`, nothing is mounted and pre-flight lists the bucket from the host (`discovery.list_s3_documents`, using the agent's listing rules) to get the count and shard plan. A host `s3_ca_bundle` is mounted read-only at `/data/s3-ca-bundle.pem` (Kubernetes copies it into a ConfigMap). Settings that depend on `source_backend` (`s3_*`, including `AWS_*` fallbacks from the scheduler's env) are rendered only for that backend.

## Modules (`src/docling_scheduler/`)

| Module | Role |
|--------|------|
| `config.py` | `SchedulerConfig.from_env()`: the `SCHEDULER_*` vars (executor, MLflow URIs, DB path, envfile, image allowlist, mount roots, Podman and `SCHEDULER_K8S_*` settings, token, allowed hosts/origins, reconcile interval, web dir) |
| `contract.py` | Vendored agent settings contract (see above) |
| `settings_io.py` | `.env` defaults without touching `os.environ`, form-value coercion against the contract, `MANAGED_KEYS` (set only by the scheduler), loopback detection and rewrite to an executor's gateway, settings → `(env, secret_env)` |
| `discovery.py` | Document count and shard plan for pre-flight (contract globs; sorted, `paths[i::N]`), local folders and S3 (boto3) |
| `preflight.py` | `run_preflight`: target, settings, document source (host folder or S3 listing), vector store, endpoints, MLflow reachability and runtime checks, driven by the executor's capabilities; renders launch inputs and a redacted preview |
| `executors/` | `Executor` protocol and `ExecutorCapabilities`; `create_executor` (picks one from config); `PodmanExecutor` (podman-py: per-run secrets as env, read-only `/data/in` and file mounts, `cap_drop=ALL`, labels `docling-agent/*`); `KubernetesExecutor` (kubernetes client: one Job per shard attempt with `backoffLimit: 0`, all run objects owned by an anchor ConfigMap `docling-run-<id>`, per-submission Secret via `secretKeyRef`, restricted pod security, cancel = suspend the Job) |
| `mlflow_monitor.py` | Parent runs, shard roll-ups and history, merged `error_reports.json`, per-document rows from traces (discovery-order cursor, not timestamps) |
| `reconcile.py` | Pure rules: merged status; RUNNING child runs of dead/superseded shards → FAILED, cancel → KILLED, parent closed when all shards are terminal |
| `service.py` / `api.py` | Launch, refresh/reconcile, cancel, retry failed shards, delete; REST + SSE logs, bearer token, Host/Origin checks, static UI |
| `registry.py` | SQLite metadata only (never secrets) |

`deploy/` holds the cluster-side install for the Kubernetes executor, as Kustomize: a base (ServiceAccount, least-privilege Role/RoleBinding, LimitRange), optional components (quota, ingress-deny NetworkPolicy, long-lived SA token, and `scheduler` (Deployment + Service) / `scheduler-fsgroup` / `scheduler-route` / `scheduler-ingress` to run and expose the scheduler itself in the namespace) and `openshift` / `kubernetes` overlays. The operator applies it; the scheduler never does. Keep the Role in sync with `_REQUIRED_ACCESS` and the calls in `executors/kubernetes.py`.

`Containerfile` builds the scheduler image in stages: docling-ui (`npm run build`), the scheduler venv (`uv sync --extra k8s`), then a UBI minimal runtime running as an arbitrary UID in group 0. `entrypoint.sh` gives every `SCHEDULER_*` variable a container default (in a pod: `kubernetes` executor, the pod's namespace). Keep it in sync with `config.py`. Off loopback, the token and the Host/Origin checks are the only guard: an exposed hostname must be in `SCHEDULER_ALLOWED_HOSTS` and `SCHEDULER_ALLOWED_ORIGINS`, and probes send `Host: localhost`.

## Commands

- `uv sync --extra dev` (add `--extra k8s` for the Kubernetes executor), then `uv run pytest`. The tests use `tests/unit/fakes.py` (executor, Podman client, in-memory Kubernetes cluster and S3 client doubles) and don't need the `kubernetes` package. There's no end-to-end suite, so real runs are tested manually under Podman or against a cluster.
- `kustomize build deploy/overlays/openshift` (and `kubernetes`) to check the manifests.
